# Prompts

Development Note

My typical development workflow is to implement the code myself first and then use AI as a reviewer to identify mistakes, suggest improvements, or discuss alternative designs. I find that writing the initial implementation helps reinforce my understanding and exposes gaps in my knowledge more effectively than reading a complete solution.

For this project, however, I adopted a different approach. Since LangGraph and multi-agent systems were completely new to me, I first studied example implementations generated by the AI before attempting to write my own code. Rather than copying the code directly, I analyzed each section, explained my understanding in my own words, received feedback on my reasoning, and only then considered implementation. This approach mirrors the way I learn in a classroom: first understanding the concepts and examples provided by the instructor, then applying that knowledge independently.

# Prompt Engineering Experiment

## Experiment

Shared a personalized learning profile with Claude based on patterns identified by ChatGPT learning sessions. The objective was to determine whether providing the model with contextual information about my preferred learning style would improve the quality of explanations throughout the project.

### Goal

Improve AI explanations by prioritizing software architecture before implementation.

### Added Instructions

This user learns by understanding architecture before implementation.

Do not jump directly into code.

Always start by explaining:
1. What problem this component solves.
2. Where it fits in the overall system.
3. Who calls it.
4. Who it calls.
5. Why it exists.

The user constantly reconstructs execution flow backwards ("Who called this?" rather than "What does this function do?"). Lean into that.

Use diagrams frequently.

Example:

User
↓
Graph
↓
Supervisor
↓
LLM
↓
Claude

instead of long paragraphs.

When introducing a class, distinguish clearly between:
- the class (type)
- an instance (object)
- when the object is created
- where it is stored

The user often asks whether something behaves like Java. Comparisons to Java are very effective because it is their strongest language.

Avoid introducing unnecessary abstractions too early.

If something could be explained with three concrete classes instead of five interfaces, do that first.

When discussing architecture, separate responsibilities carefully.

Example:
- Graph orchestrates.
- Agents make decisions.
- LLM generates text.
- Provider chooses implementation.
- Mock simulates responses.

The user enjoys reconstructing software architecture more than memorizing syntax.

When explaining a new file, first answer:
"What is its responsibility?"

Only then explain methods.

The user appreciates reasoning about why a design was chosen, not just how it works.

When possible, relate new concepts to previous components already understood.



Examples should be small.

Avoid giant code listings.

Prefer building the system incrementally.

Good sequence:

Concept
↓

Diagram
↓

Small example
↓

Real project example
↓

Actual code



Do not assume understanding after one explanation.

The user likes asking follow-up questions to refine their mental model.

Treat those questions as progress, not confusion.

### Outcome

The explanations became noticeably easier to follow. Claude began introducing new concepts by explaining the overall architecture before discussing implementation details, using diagrams and separating component responsibilities more consistently. This made the learning process feel more natural and reduced the amount of clarification needed during discussions.
